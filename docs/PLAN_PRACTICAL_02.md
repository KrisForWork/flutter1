# Практическая работа №2 — Типы тестирования  
## Подробный план разработки (без реализации кода)

**Статус:** реализация и тесты готовы; review выполнен (`docs/REVIEW.md`, `docs/REPORT.md`)  
**Проект:** `test1` (Flutter)  
**Тема:** ручное тестирование, автотестирование, нагрузочное тестирование  
**Цель:** на одном приложении-справочнике показать три типа тестирования — что проверяем, чем пользуемся, как оформляем результат

### Зафиксированные решения

| Вопрос | Решение |
|--------|---------|
| Тема приложения | **Справочник** (каталог записей) |
| Автотесты | только **unit + widget** (без integration_test) |
| Нагрузка | только **клиентская** |
| UI | **с фильтрами** + **отдельный экран нагрузки** |
| Язык интерфейса | **русский** |

## 1. Суть задания

Нужно не просто «написать тесты», а **разобрать три типа тестирования** и для каждого показать:

| Тип | Что это | Что использовать | Что в отчёте |
|-----|---------|------------------|--------------|
| Ручное | Человек проверяет сценарии по чек-листу | приложение + чек-лист + баг-репорт | заполненный чек-лист |
| Автоматическое | Код проверяет логику и UI | `flutter_test`: **unit + widget** | код тестов + вывод `flutter test` |
| Нагрузочное | Поведение под нагрузкой на клиенте | `Stopwatch`, массовые операции, экран «Нагрузка» | таблица времени, выводы |

---

## 2. Идея приложения — «Справочник»

Учебное приложение **«Справочник»**: каталог записей (термин / статья) с категориями, поиском и фильтрами.

### 2.1. Модель записи

`DirectoryEntry` (запись справочника):

| Поле | Тип | Смысл |
|------|-----|--------|
| `id` | `String` | уникальный id |
| `title` | `String` | название (термин) |
| `description` | `String` | краткое описание |
| `category` | `String` | категория (например: «Тестирование», «Flutter», «Общее») |
| `isFavorite` | `bool` | избранное |

### 2.2. Экраны и функции

1. **Главный экран — список справочника**
   - список записей
   - пустое состояние: «Нет записей»
   - счётчик: всего / избранных (по текущему фильтру)

2. **Фильтры** (обязательно)
   - категория: Все / выбранная категория
   - избранное: Все / Только избранные
   - поиск по названию (подстрока, без учёта регистра)
   - комбинация фильтров работает вместе

3. **Добавление / редактирование (минимум — добавление)**
   - поля: название, описание, категория
   - валидация: название не пустое (после `trim`)
   - пустое название не добавляется

4. **Действия с записью**
   - открыть детали (просмотр)
   - добавить / убрать из избранного
   - удалить запись

5. **Отдельный экран «Нагрузка»** (обязательно)
   - выбрать N: 100 / 1_000 / 10_000
   - «Сгенерировать N записей»
   - «Очистить справочник»
   - «Применить фильтр к большому списку» (замер)
   - вывод времени операции в мс
   - переход с главного экрана (кнопка / пункт меню)

### 2.3. Почему справочник

- понятная тема для отчёта («каталог знаний»);
- фильтры и поиск дают богатые unit/widget-кейсы;
- избранное и категории — удобные ручные сценарии;
- массовая генерация записей — клиентская нагрузка без сервера;
- UI на русском хорошо смотрится в учебной сдаче.

### 2.4. Стартовые демо-данные (небольшая выборка)

Несколько записей про тестирование, например:
- «Unit-тест», «Widget-тест», «Чек-лист», «Нагрузочное тестирование»  
чтобы ручное тестирование можно было начать сразу.

## 3. Разбиение на подзадачи

### Этап A — Подготовка (после финального «ок»)

| ID | Подзадача | Результат |
|----|-----------|-----------|
| A1 | Структура папок | `lib/`, `test/`, `docs/` (без `integration_test/`) |
| A2 | Зависимости | только `flutter_test` + `flutter_lints` |
| A3 | Линтер под стандарты | `analysis_options.yaml` |
| A4 | Убрать шаблон counter | чистый `main.dart` |

### Этап B — Реализация приложения

| ID | Подзадача | Результат |
|----|-----------|-----------|
| B1 | Модель `DirectoryEntry` | поля + `copyWith` |
| B2 | `DirectoryRepository` (in-memory) | add / remove / toggleFavorite / filter / search / seed / clear / generate |
| B3 | `DirectoryController` (`ChangeNotifier`) | состояние UI, фильтры, навигация данных |
| B4 | Экран списка + фильтры + поиск | русский UI |
| B5 | Форма добавления записи | валидация названия |
| B6 | Экран деталей записи | просмотр + избранное + удаление |
| B7 | **Отдельный экран «Нагрузка»** | генерация N, очистка, замеры |
| B8 | `Key` для виджетов | стабильные селекторы для widget-тестов |
| B9 | Smoke-запуск | Windows / Web / Android при наличии |

### Этап C — Ручное тестирование

| ID | Подзадача | Результат |
|----|-----------|-----------|
| C1 | Чек-лист | `docs/manual/CHECKLIST.md` |
| C2 | Шаблон баг-репорта | `docs/manual/BUG_REPORT_TEMPLATE.md` |
| C3 | Прохождение чек-листа | `docs/manual/CHECKLIST_RESULTS.md` |
| C4 | Вывод в отчёт | плюсы/минусы ручного тестирования |

**Что и как использовать (ручное):**

- чек-лист: действие → ожидаемый результат;
- эквивалентные классы: пустой / нормальный / длинный ввод, «только пробелы»;
- границы: 0 записей, 1 запись, много записей;
- фильтры: каждая категория, избранное, поиск, комбинации;
- smoke: открытие приложения, добавление, фильтр;
- инструменты: само приложение, Markdown, скриншоты; DevTools Inspector по желанию.

### Этап D — Автотестирование (unit + widget)

| ID | Подзадача | Результат |
|----|-----------|-----------|
| D1 | Unit: модель / репозиторий / фильтры | `test/unit/...` |
| D2 | Widget: список, фильтры, добавление | `test/widget/...` |
| D3 | Прогон | `flutter test` → `docs/auto/TEST_RUN.md` |
| D4 | Вывод в отчёт | пирамида тестов (без integration) |

**Что и как использовать (авто):**

| Уровень | API | Что проверяем |
|---------|-----|----------------|
| Unit | `test` / `flutter_test` | add, remove, favorite, filter, search, generate |
| Widget | `WidgetTester`, `find`, `Key` | UI: поиск, фильтр, добавление, пустое состояние |

**Не делаем:** `integration_test`, e2e на устройстве.

Команда:

```bash
flutter test
```

### Этап E — Нагрузочное тестирование (только клиент)

| ID | Подзадача | Результат |
|----|-----------|-----------|
| E1 | `generate(n)` в репозитории | массовое создание записей |
| E2 | Замер на экране «Нагрузка» | N = 100 / 1_000 / 10_000 |
| E3 | Load unit-тест с `Stopwatch` | `test/load/...` |
| E4 | Наблюдение UI при большом списке | scroll, лаги |
| E5 | Отчёт | `docs/load/LOAD_REPORT.md` |

**Что и как использовать (нагрузка):**

- стресс логики: много `add` / `generate` / `filter` без UI;
- стресс UI: большой список + `ListView.builder`;
- метрики: время мс, N, среда запуска;
- инструменты: `Stopwatch`, экран «Нагрузка», DevTools Performance.

**Не делаем:** JMeter / k6 / серверный load (в отчёте можно одной фразой отличить клиентскую нагрузку от серверной).

### Этап F — Итоговый отчёт

| ID | Подзадача | Результат |
|----|-----------|-----------|
| F1 | Сводный отчёт | `docs/REPORT.md` |
| F2 | Сравнительная таблица трёх типов | плюсы / минусы / когда применять |
| F3 | Инструкция запуска | раздел в отчёте / README |
| F4 | `flutter analyze` + `flutter test` | зелёные |

## 6. Критерии готовности

1. Справочник на русском: список, фильтры, поиск, добавление, избранное, удаление, детали.  
2. Есть отдельный экран «Нагрузка» с замерами.  
3. Заполнен чек-лист ручного тестирования.  
4. Unit + widget тесты зелёные (`flutter test`).  
5. Отчёт по клиентской нагрузке для N = 100 / 1_000 / 10_000.  
6. Сводный `REPORT.md` со сравнением трёх типов.  
7. Код по `FLUTTER_STANDARDS.md`, `flutter analyze` без ошибок.
