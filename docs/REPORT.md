# Отчёт по практической работе №2  
## Типы тестирования на приложении «Справочник»

**Проект:** `test1` (Flutter)  
**Тема:** ручное, автоматическое (unit + widget) и клиентское нагрузочное тестирование  
**UI:** русский  

---

## 1. Приложение

Учебный **справочник** записей (термин / статья): категории, поиск, избранное, добавление, детали, удаление и отдельный экран **«Нагрузка»** для генерации N записей и замера фильтра в памяти.

Архитектура: `DirectoryRepository` → `DirectoryController` (`ChangeNotifier`) → UI-виджеты.

---

## 2. Ручное тестирование

**Определение.** Проверка сценариев человеком по заранее составленному чек-листу.

**Цель.** Найти UX/визуальные дефекты, проверить smoke и комбинации фильтров «глазами».

**Инструменты и артефакты**

| Артефакт | Путь |
|----------|------|
| Чек-лист | `docs/manual/CHECKLIST.md` |
| Результаты | `docs/manual/CHECKLIST_RESULTS.md` |
| Шаблон баг-репорта | `docs/manual/BUG_REPORT_TEMPLATE.md` |

**Как применяли.** P0 smoke (старт, демо-данные, счётчик, добавление, экран нагрузки); P1 фильтры/поиск/добавление/детали/нагрузка; P2 границы. Часть кейсов подтверждена автотестами; полный device-run в сессии разработки/тестирования помечен честно в `CHECKLIST_RESULTS.md`.

**Плюсы:** ловит то, что автотесты не видят (лаги UI, читаемость).  
**Минусы:** субъективно, долго, плохо масштабируется.  
**Когда:** регрессия UX, первый smoke, приёмка.

---

## 3. Автоматическое тестирование (unit + widget)

**Определение.** Код проверяет логику и UI без ручных кликов.

**Цель.** Стабильно регрессировать фильтры, валидацию, список, форму, детали, экран нагрузки.

**Инструменты:** `flutter_test` (`test`, `WidgetTester`, `Key`).  
**Не используем:** `integration_test`.

| Уровень | Где | Что |
|---------|-----|-----|
| Unit | `test/unit/` | модель, repository (add/trim/filter/search/favorite/generate/clear), controller |
| Widget | `test/widget/` | пустой список, поиск, фильтры, combo, добавление, валидация, детали, Load |
| Load* | `test/load/` | замеры generate/filter (см. §4) |

\*Load-тесты — часть клиентской нагрузки, запускаются тем же `flutter test`.

**Результаты:** см. `docs/auto/TEST_RUN.md` — `flutter test` зелёный; `flutter analyze` без замечаний.

**Плюсы:** быстро, повторяемо, хорошо ловит логические регрессии.  
**Минусы:** не заменяют ручной UX и реальный FPS.  
**Когда:** CI, рефакторинг логики фильтров, валидации.

**Пирамида (урезанная под задание):**

```text
      /\
     /  \   widget
    /----\
   /      \ unit
  ----------
  (без integration)
```

## 4. Нагрузочное тестирование (только клиент)

**Определение.** Оценка поведения приложения при большом объёме данных **на устройстве/в VM**, без сервера.

**Цель.** Измерить время `generate(N)` и `filter` для N = 100 / 1 000 / 10 000.

**Инструменты:** `Stopwatch`, экран «Нагрузка», `test/load/`, `ListView.builder`.  
**Не используем:** JMeter / k6 / HTTP load.

**Артефакт:** `docs/load/LOAD_REPORT.md`.

**Типичные замеры логики (VM, `flutter test`, Windows):**

| N | generate, мс | filter, мс |
|---|--------------|------------|
| 100 | ~1 | ~1 |
| 1 000 | ~3–4 | ~1 |
| 10 000 | ~18–19 | ~8–15 |

**Плюсы:** просто показать «узкое место» на клиенте.  
**Минусы:** не моделирует сервер и сеть; UI-FPS нужно смотреть отдельно (DevTools).  
**Когда:** оценка in-memory операций и готовности списка к большим N.

---

## 5. Сравнение трёх типов

| Критерий | Ручное | Авто (unit/widget) | Нагрузка (клиент) |
|----------|--------|--------------------|-------------------|
| Кто выполняет | человек | код (`flutter_test`) | код + экран «Нагрузка» |
| Что ловит лучше | UX, тексты, визуал | логика, регрессии API/UI | время операций при большом N |
| Скорость прогона | медленно | быстро | средне (зависит от N) |
| Повторяемость | низкая | высокая | высокая для логики |
| Стоимость поддержки | чек-листы | тесты как код | метрики + сценарий N |
| Когда выбирать | приёмка, exploratory | каждый commit / CI | перед сдачей «больших списков» |
| Ограничение в работе | device-run желателен | без integration | без серверного load |

## 6. Как запустить

```bash
# из корня проекта test1
flutter pub get
flutter analyze
flutter test

# только нагрузка
flutter test test/load/directory_repository_load_test.dart

# приложение (Windows / Chrome / Android — что доступно)
flutter run
```

В приложении: список → иконка спидометра → экран «Нагрузка» → выбрать N → «Сгенерировать» / «Применить фильтр» / «Очистить».
